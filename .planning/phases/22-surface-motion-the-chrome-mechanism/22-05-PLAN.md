## Planner decisions

**OQ3 — header out-of-flow via `position: absolute`, not a collapsing wrapper.** One element, no new
wrapper node, and the `inert` / `aria-hidden` props live on the same element the CHROME-04 assertion
targets. `22-VALIDATION.md`'s CHROME-04 row and `22-RESEARCH.md` §Code Examples both assert
`position: absolute` on `role="banner"`; `22-UI-SPEC.md`'s table says "fixed". **`absolute` wins** —
both are out of flow, the assertion must pin one string, and `absolute` avoids the Phase-21 D-28
transform-ancestor trap that `fixed` would expose. `AppShell`'s root column is unpositioned and the
document itself never scrolls (`<main>` owns the scrolling), so `top: 0` is stable.

**D-13 vs the out-of-flow header — resolved, and this is the plan's one genuine conflict.**
`env(safe-area-inset-top)` is reserved today by **exactly one thing**: the header's own
`paddingTop: calc(env(safe-area-inset-top) + 12px)` (`AppShell.tsx:48`). The instant the header leaves
the flow, nothing reserves it, `<main>` starts at viewport y=0, and the constellation runs under the
notch — breaking D-13 ("the top safe-area inset stays; the constellation does NOT run under the
notch"). This is invisible on a desktop, where the inset is `0`.

**Decision: while chrome is hidden, `<main>` reserves a bare `env(safe-area-inset-top)`.**
  - It is a **bare read, not new arithmetic.** The rule this phase inherits (D-13: "introduce no
    second top-inset *expression*") is about not inventing a second `calc(env(...) + N)` formula that
    can drift from the shipped one. A bare `env(safe-area-inset-top)` is the app's existing
    per-surface top-inset idiom — there are already ~10 such reads in `src/`.
  - The Phase-21 FOUND-02 source guard in `bottomSpace.test.ts` forbids only
    `env(safe-area-inset-bottom)`; top/left/right insets are explicitly out of its scope. This adds no
    guard violation.
  - It lands in the **same commit** as the reserve collapse and the flow change, so the one-resize
    claim (CHROME-05) still holds.
  - **Rejected for this phase:** hoisting `env(safe-area-inset-top)` into a `--gz-safe-top` on `:root`
    (mirroring `--gz-safe-bottom`). It is the better long-term shape, but it touches ten surfaces
    including five device-verified sheets and can change where the header's `bg-elevated` starts
    painting. **Record it as a follow-on todo at phase close; do not do it here.**

**D-08's "unmount at end" clause is deliberately NOT implemented; the chrome stays mounted and
`inert`.** A reasoned deviation, recorded so nobody reads it as an oversight:
  - D-08's operative rule — *hidden chrome leaves the accessibility tree at animation START* — is
    honoured exactly, by `inert` + `aria-hidden` + `pointer-events: none` applied in the same commit as
    the reserve collapse. That is also literally what CHROME-04 asks for, and `inert` is the mechanism
    `22-RESEARCH.md` §Pattern 6 names for it.
  - Unmounting via `AnimatePresence` would make the START half **impossible** — this is §Pitfall 14
    applied to chrome. React renders a removed `AnimatePresence` child from a **frozen element**, so
    the exiting header would keep `inert={false}` and `position: relative` for the whole 200ms, which
    is the exact regression D-08 exists to prevent. Moving the attributes onto an always-rendered
    wrapper would hide them from CHROME-04's `role="banner"` assertion.
  - **Because chrome is never an `AnimatePresence` child, §Pitfall 14 does not apply to any value in
    this plan** — every prop here re-renders normally on a store change. Say so in a source comment so
    a future reader does not "helpfully" add `AnimatePresence`.
  - Staying mounted also avoids remounting `BottomTabBar` (and re-subscribing `useHashRoute`) on every
    toggle.

**`BottomTabBar` subscribes to the store itself rather than taking a new prop.** Its exported
signature stays zero-arg, so `packages/app/test/bottomSpace.test.ts`'s `createElement(BottomTabBar)`
and `packages/app/test/bottomOverlayInset.test.tsx`'s renders keep compiling. That matters for wave
scheduling: `bottomOverlayInset.test.tsx` belongs to plan 22-08 in a later wave and must not be forced
open by this plan. Both `AppShell` and `BottomTabBar` read the same cached scalar and re-render in the
same commit when the store notifies, so the one-commit collapse is preserved.
