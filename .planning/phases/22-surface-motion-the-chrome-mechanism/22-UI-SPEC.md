# Phase 22 — UI Design Contract

> Visual and interaction contract for **Surface Motion & the Chrome Mechanism** — the shared
> `<Sheet>` primitive animates without losing an accessibility guarantee, the chrome-hide
> mechanism debuts on GizzVerse with its escape and a11y invariants provable, and the
> add-to-home-screen path relocates to the bottom of Settings. Generated by gsd-ui-researcher;
> verified by gsd-ui-checker.
>
> **This is a motion + mechanism phase, not a new-screen phase.** It ships **zero new screens,
> zero new colors, zero new type roles, and zero new runtime dependencies** (`motion` 12.42 is
> already a dependency — D-23). It ships **one new z-tier (`chrome: 14`, no renumbering), one new
> control (`ChromeToggle`), one relocated section (Settings → install), and one motion token
> group (`config.ui.motion`).**
>
> Every token below is either **DETECTED** from the shipped Guezzer design system
> (`packages/app/src/styles.css` `@theme`, `packages/app/src/config.ts`, `21-UI-SPEC.md`) or
> **DERIVED** from the 38 locked decisions in `22-CONTEXT.md` (D-01…D-38). Nothing in
> `22-CONTEXT.md` §Decisions was re-asked. The four items `22-CONTEXT.md` explicitly delegates to
> **Claude's Discretion** — the toggle icon, the Settings install-section styling, the easing
> curve + `config.ui` constant names, and the internal shape of the chrome-visibility module —
> are decided here and marked **[DISCRETION]**.

## Iconography **[DISCRETION]**

| Icon | Where | Why this glyph |
|------|-------|----------------|
| `Maximize2` (24px) | `ChromeToggle` while chrome is **visible** (tap = hide bars) | The universal expand-viewing-area affordance. Carries D-06's "no discovery affordance needed" claim on its own — a user who has ever seen a video player recognizes it. |
| `Minimize2` (24px) | `ChromeToggle` while chrome is **hidden** (tap = show bars) | The exact inverse glyph, so the control reads as a single toggle rather than two different buttons. |
| `Smartphone` (18px button / 20px row) | Settings install button **and** the `AppMenu` "Add to Home Screen" row | Names the *destination* (your phone's home screen), matching D-34's "name where it goes, not what it does". |

Collision check — none of the three is used anywhere in the app today. Deliberately **rejected**:

- `Download` for the install button — already the Settings **Export** CTA icon **in the same view**;
  two `Download` glyphs in one screen with different meanings is a legibility bug.
- `Expand` / `Shrink` — newer lucide glyphs with a weaker recognition base than `Maximize2`.
- `ChevronsUpDown` — reads as "sort" / "reorder", not "hide chrome".

The glyph is `aria-hidden` in all three places; the accessible name is carried by the button's
`aria-label` or its visible text label (never by the icon).

## Motion Token Contract **[DISCRETION]**

**All motion constants live in a new `config.ui.motion` group.** `WaveToast.tsx:167`'s hard-coded
`transition={{ duration: 0.2 }}` is exactly the scattered magic number CLAUDE.md forbids — it is
**moved here, not copied** (D-25).

| Constant | Value | Applies to |
|----------|-------|-----------|
| `SHEET_DURATION_MS` | `200` | Sheet enter, sheet exit, and the scrim cross-fade — **one duration, run in parallel** (D-24) |
| `SHEET_EASE_ENTER` | `"easeOut"` | Sheet enter + scrim fade-in — decelerates into place |
| `SHEET_EASE_EXIT` | `"easeIn"` | Sheet exit + scrim fade-out — accelerates away |
| `CHROME_DURATION_MS` | `200` | Header / tab-bar slide, both directions |
| `CHROME_EASE_HIDE` | `"easeIn"` | Chrome sliding out |
| `CHROME_EASE_SHOW` | `"easeOut"` | Chrome sliding in |
| `TOAST_DURATION_MS` | `200` | `WaveToast`'s relocated `0.2` (D-25) |

Notes:

- Named `motion` string easings (`"easeIn"` / `"easeOut"`) are chosen over cubic-bezier tuples
  **on purpose**: at 200ms the perceptual difference from a hand-tuned curve is nil, and a named
  easing states its intent in the config file rather than requiring four magic numbers to be
  decoded. This is the "same curve family the app's toasts already use" that D-24 asks for —
  `WaveToast` today runs `motion`'s default tween easing at the same 200ms.
- `motion` takes seconds: consumers write `duration: config.ui.motion.SHEET_DURATION_MS / 1000`.
  **The `/ 1000` conversion happens at the consumer, and the config value stays in ms** — the unit
  every other timing constant in `config.ts` already uses.
- **200ms is a ceiling, not a target to grow.** D-24's reasoning is that the close-start window in
  which a stray tap can land (§Sheet Timing Contract) must stay short. Any future increase must
  re-argue SHEET-02.

## Sheet Motion Contract (SHEET-01)

Scope: **the shared `<Sheet>` primitive only — the 15 importing surfaces.** The five hand-rolled
sheets (`SearchSheet`, `AlbumDetail`, `ArchiveBrowser`, `SetlistView`, `NodeSheet`) stay static
(D-16, honoring Phase-21 D-22). **`SearchSheet` visibly not animating while everything else does is
a named, accepted seam** — recorded here so the first person to notice it finds the reason instead
of "fixing" it by copying the animation into five more files.

### Per-variant motion

| Variant | Enter | Exit | Reduced motion |
|---------|-------|------|----------------|
| `bottom-sheet` **card** | `y: "100%" → 0`, opacity unchanged | `y: 0 → "100%"` | `opacity: 0 → 1` / `1 → 0`, **no translate** |
| `bottom-sheet` **scrim** (`backdrop`) | `opacity: 0 → 1`, **parallel with the card, same duration** | `opacity: 1 → 0`, parallel | `opacity: 0 → 1` / `1 → 0` (identical — the scrim never moved) |
| `fullscreen` | `opacity: 0 → 1`, **no translate** (D-26) | `opacity: 1 → 0` | identical to the non-reduced path |

- **`y` is a percentage of the sheet's own height**, never a measured pixel value — the primitive
  owns no content layout and must not start measuring it.
- **Parallel, never staged** (D-24). A scrim that lags the card leaves a painted scrim after the
  sheet is gone, which would make `pointer-events: none` on the first exit frame a subtle,
  easily-regressed rule instead of a structural one.
- **`fullscreen` fades because a full-bleed overlay sliding a whole viewport height reads as a page
  transition, not a sheet** (D-26). SHEET-01's wording is "every bottom **sheet**". Live fullscreen
  consumers: `CompareView` (×2), `DexView`, `FriendDetail` (×2).
- **Reduced motion keeps an opacity cross-fade, and that is the correct reading of "without
  motion"** — WCAG "motion" means movement, and this is the shipped `WaveToast:164-166` idiom
  (D-24). It is *not* the chrome rule: chrome under reduced motion is **instant** (D-07). One phase,
  two surfaces, two justified answers — both recorded so neither is later "unified" by mistake.
- **Stacked-sheet scrims are left exactly as they ship** (D-28). Two open sheets paint two scrims
  and the background reads darker; the only change is that the second scrim now fades in.

## Sheet Timing Contract (SHEET-02) — the phase's single hardest invariant

> **One timing rule for the whole phase: a surface leaves the accessibility tree and stops being a
> pointer target at the START of its exit, and leaves the DOM only at the END.** (D-19 for sheets,
> D-08 for chrome — if a planner writes two different rules, one of them is wrong.)

### Close-START — everything in this table fires in the same tick `onClose` is requested

| # | What flips | Why |
|---|-----------|-----|
| 1 | Background `inert` **released** (`useFocusTrap`'s ref-counted helper) | The background must be tappable *during* the exit window — SHEET-02's literal demand |
| 2 | Focus **restored to the trigger** | A screen-reader user is never left on a disappearing element |
| 3 | Exiting sheet gets `aria-hidden="true"` | VoiceOver must not read a sheet that is on its way out |
| 4 | Exiting sheet **and** scrim get `pointer-events: none` | A tap in the exit window reaches the real background, never a ghost |
| 5 | *(nothing else)* | — |

### Close-END (after `SHEET_DURATION_MS`)

| # | What happens |
|---|--------------|
| 6 | `AnimatePresence` removes the DOM node. **This is the only thing that waits.** |

**Implementation consequence the planner must not miss:** `useFocusTrap` today performs items 1, 2
and unmount *together* on deactivate. That teardown must be **split** from unmount, not merely
delayed with it (D-19). `Sheet.tsx`'s `if (!open) return null` guard (V7 / T-08-04) is what makes an
exit animation impossible today and is replaced by `AnimatePresence`'s deferred unmount (D-23) —
the closed-sheet-renders-nothing and never-throws properties must survive that replacement.

### Enter timing

| Moment | What happens |
|--------|--------------|
| Enter-START | Sheet is mounted, **interactive, and in the a11y tree immediately.** Focus trap + `inert` engage now. |
| Enter-END | **`initialFocusRef` focus fires here only** (D-27) — `SettingsView`'s name input and `PinSheet`'s label input open the iOS keyboard, and focusing a translating element races two layout changes on the platform where this app's viewport math has already misfired. Accepted cost: ~200ms before the user can type. |

Sheets without an `initialFocusRef` keep `useFocusTrap`'s shipped initial-focus-on-activate
behavior at enter-START — so a keyboard user is never stranded outside the sheet mid-animation.

### Interruption (D-22)

Interrupting the enter **closes immediately, reversing from the current position**. `AnimatePresence`
animates out from wherever it is — no queueing, no waiting, no interrupted-open special case. The
close-START teardown above fires as normal. Input is never ignored, which matters most in the dark
at a venue.

### Asserted every commit (D-20)

A jsdom test opens a sheet, requests close, and **before the exit completes** asserts: background not
`inert`, focus back on the trigger, sheet `aria-hidden`, sheet and scrim both `pointer-events: none`.
The device session (§Device Verification) proves it once on real VoiceOver; this keeps it true
forever. A *source-text* guard was considered and rejected — Phase 21 learned that pattern-matching
guards cannot catch a surface that simply omits the thing (the `ArchiveBrowser` bug, `61e0b90`).

### Non-goals, recorded so they are not re-proposed

- **No swipe-down-to-dismiss** (D-29). In tension with Phase 23's INSHOW-03; the primitive
  deliberately owns no drag geometry.
- **No runtime kill-switch, no feature flag** (D-18). "Backable-out" means a clean revert of the
  exit commit, leaving an enter-only build — the degraded ship SHEET-02 explicitly sanctions.
  `prefers-reduced-motion` remains a genuine user-controlled no-motion mode at zero extra cost.
- **Heavy-content sheets ship as-is** (D-30). `ShareCardSheet`'s PNG pre-build and `CompareView`'s
  `deriveDex` re-run are pre-existing; the animation adds no work, it only makes an existing hitch
  legible. Observe on device, fix only what stutters. The `ShareCardSheet` pre-build must **not** be
  deferred to "fix" a jank nobody has seen (Phase-6 Pitfall 7).
- **`modal={false}` / `backdrop={false}` keep their capability, and the stale doc comment is
  corrected** (D-31). Every live `<Sheet>` consumer passes `modal`; the prop doc's claim about "the
  NodeSheet variant" has **zero live consumers**. Say plainly that the path is currently
  unexercised so nobody reads it as verified.

## Chrome Mechanism Contract (CHROME-01/03/04/05)

### `ChromeToggle` — the one control

| Property | Value | Source |
|----------|-------|--------|
| Placement | **Fixed, top-right, aligned with the header's control row** — `top: calc(env(safe-area-inset-top) + 12px)`, `right: calc(env(safe-area-inset-right) + 16px)` | D-01 (never moves) + D-02 (top-right) + D-13 (no new top-inset arithmetic) |
| Size | **44 × 44** (`config.ui.chrome.CHROME_TOGGLE_SIZE_PX`), `min-h-11 min-w-11` | CHROME-03 |
| Shape / fill | `rounded-full border border-hairline bg-elevated text-text-primary touch-manipulation focus-visible:outline-2 focus-visible:outline-accent` — the `ExploreFilterFab` treatment at a smaller diameter | §Color; `ExploreFilterFab.tsx:136` |
| Glyph | `Maximize2` when chrome visible · `Minimize2` when hidden, 24px, `aria-hidden` | **[DISCRETION]** §Iconography |
| Accessible name | `"Hide bars"` when visible · `"Show bars"` when hidden — **the label always names what the tap will do** | D-05 |
| z-index | `config.ui.z.fab` (30) | Above the sliding chrome (`chrome: 14`), below any sheet |
| Rendered by | **`ExploreView`, as the FIRST child of its returned fragment** | D-03 (the view opts in) + tab-order rule below |
| Mounted | **Always, in both states.** Never conditionally rendered, never `visibility: hidden`, never moved. | CHROME-03 |

**Why the header band and not "inside the stage box":** D-01 requires *the same pixel in both
states*. The stage's top edge moves up by the header's height the instant chrome collapses (D-07),
so any stage-anchored control moves with it. Anchoring to the viewport at the app's shipped
`calc(env(safe-area-inset-top) + 12px)` offset is the only placement that is provably constant
**and** adds no new top-inset arithmetic — this project has been bitten by top-inset math twice
(UX-01/D-01's doubled inset, the Phase-21 bookmark-vs-standalone confusion). While chrome is
visible the toggle reads as a third header control; while hidden it floats over the constellation at
the identical pixel.

**The header reserves horizontal room for it.** While a toggle is registered, `AppShell`'s
right-hand control cluster gets `paddingRight: config.ui.chrome.CHROME_TOGGLE_SLOT_PX` (52px = 44 +
8) so the toggle never overlaps the menu button. The reservation is driven by the shared
chrome-visibility store (below) — **not** by `ExploreView` reaching into `AppShell`, and **not** by
an `AppShell` header slot (a slot's contents would vanish with the header, which is fatal for
CHROME-03).

**Tab order (CHROME-03).** The toggle is the first child of `ExploreView`'s fragment, so DOM order
alone makes it the first focusable element inside `<main>`. In the **hidden** state — the state
CHROME-03 is about — the header is `inert`, so the toggle is the **first focusable element in the
document**. Asserted by test. **No positive `tabindex`** anywhere: that is an a11y anti-pattern and
this control is the last place to introduce one.

**Never sticky (CHROME-03).** Hidden state is plain component state — no `sessionStorage`, no
`db.meta` row, no storage key (D-11). "A cold boot never starts hidden" is true **by construction**,
not by a rule someone must maintain. Leaving GizzVerse resets it. Accepted cost: switching to Map
and back is one extra tap to re-hide.

**Escape restores chrome** via the app's shipped LIFO dismiss stack (`useDialogDismiss`), so a
keyboard user gets the same out they get from every sheet (D-04). **The OS back gesture is
deliberately left alone** — hijacking it needs a history entry, and this app has hash-only
navigation with no router. Phase 23's INSHOW-02 builds that mechanism once, deliberately.

**No discovery affordance** (D-06) — no hint, no once-per-build flag, no dismissal state. The glyph
carries it, and the cost of missing it is zero (the app works exactly as it does today). The app
already carries one onboarding nag whose gating logic took two rounds to settle.

### What "chrome" means

**App chrome only: the `AppShell` header + `BottomTabBar`.** `ExploreFilterFab` **stays visible**
(D-10) — the edge slider and top-K declutter matter most in immersive mode. This is also the only
definition that means the same thing for Phase 23's live-show consumer.

**The top safe-area inset stays** (D-13). Only the header *bar* disappears; the stage still starts
below the status bar. The constellation does not run under the notch, and the toggle needs no
special offset to stay inside the safe area.

### The hide/show sequence — one resize, by construction (CHROME-05, CHROME-04)

**Hide** (tap "Hide bars"):

| Frame | What happens |
|-------|--------------|
| **0 (same tick)** | 1. `chromeVisible → false` in the shared store. `--gz-chrome-reserve` collapses to `var(--gz-safe-bottom)`; `<main>`'s top reservation collapses to the safe-area inset only. **The canvas container gets its full height here — exactly ONE `ResizeObserver` callback.** |
| **0 (same tick)** | 2. Header and `BottomTabBar` get `inert` + `aria-hidden="true"` + `pointer-events: none`, and switch to `position: fixed` (out of flow, holding no layout). **They leave the a11y tree before they finish leaving the screen** (D-08 = D-19's rule). |
| **0 → 200ms** | 3. Header `translateY(0 → -100%)`, tab bar `translateY(0 → 100%)`, `CHROME_EASE_HIDE`. **Pure transform — costs no layout, fires no further resize.** |
| **200ms** | 4. `AnimatePresence` unmounts both. |

**Show** ("Show bars") is the exact reverse: box expands at frame 0 (one resize), chrome mounts
interactive and in the a11y tree immediately, slides in with `CHROME_EASE_SHOW` over 200ms.

**Reduced motion:** steps 2–4 collapse into frame 0 — chrome is removed instantly, no fixed-position
phase (D-07). One resize either way.

**This ordering is the whole point.** Animating the layout box would produce a continuous stream of
`ResizeObserver` callbacks; collapsing the box first and animating a transform over it makes
CHROME-05's assertion true by construction rather than by careful debouncing.

**Asserted by test, not by device (D-09).** A jsdom test toggles chrome and asserts (a) the
container resize callback fires **exactly once** and (b) `zoomToFit` is **not** re-called. The
requirement's own wording is "asserted by test", the simulation is already structurally safe
(`ConstellationCanvas` pins `fx`/`fy` at `onEngineStop`; `hasFitRef` gates the camera against resize
snaps, UX-04), and this phase already budgets two device items.

### Riders — surfaces that follow for free

| Surface | Behavior when chrome hides | Why |
|---------|---------------------------|-----|
| `NodeSheet` (open, focused node) | **Stays open and settles down into the freed space** | It is `fixed bottom-0` composing from `--gz-chrome-reserve`; collapsing the reserve moves it for free. Non-modal, so nothing about focus or Escape changes (D-14). Pinning it in place was rejected — that means re-introducing a hand-written offset in the one place Phase 21 just finished eliminating. |
| Toasts / `InstallBanner` / `UpdateToast` | **Render at the collapsed position; chrome stays hidden** | They compose from `--gz-chrome-reserve`, which has collapsed to bare safe-area, so they simply sit lower. No special case, no code (D-15). Forcing chrome back was rejected — it yanks the user out of a state they deliberately entered, and one of those events is the update prompt, which must never surprise-swap the app mid-show. Suppressing toasts was rejected — the update prompt is a safety surface. |
| `ExploreFilterFab` | Unchanged, stays visible, follows the collapsed reserve | D-10 |
| Rotation-empty overlay | Unchanged (`fixed inset-0`, centered) | Stays legible with chrome hidden |

## Layering Contract

## Bottom-Overlay Stack Order (folded todo CR-01)

The Phase-21 store already measures every registered overlay's height but has **no ordering
concept**, so two visible overlays overlap while `<main>` over-reserves their sum. This phase gives
the registrations a **declared order in `config.ui`** and offsets each overlay by the summed height

|-------|-----------------|-----------|
| 1 (bottom-most) | `installBanner` | Persistent, not transient — it must not jump when a transient toast appears |
| 2 | `updateToast` | The safety surface; never suppressed, never covered |
| 3 | `backupToast` | |
| 4 | `bingoCelebration` | |
| 5 (top-most) | `waveToast` | The most transient |

Each overlay composes `bottom: calc(var(--gz-chrome-reserve) + <sum of visible heights below>px)`.

## Install Affordance Contract (NAV-05, NAV-06)

### Settings — the new install section **[DISCRETION on styling]**

**Position:** a new top-level `<section>`, the **last** child of `SettingsView`'s column, below
owner identity → data/export → rotation reset (D-32). It inherits the container's shipped
`gap-6` / `pb-16`.

**Gate:** the whole section is hidden once installed. It and the `AppMenu` row read **one** shared
gate so they can never disagree.

**Structure** — one section, one heading, three platform-adaptive bodies:

```
<section id="install">                     ← the D-35 deep-link target
  <h2 tabIndex={-1}>Add to Home Screen</h2>   ← 20px/600, focus lands HERE
  <p>{description}</p>                        ← 16px/400 muted
  ── one of ──
  [Install Gizz With Friends]  ← Android: beforeinstallprompt captured. NEUTRAL button,
                                 min-h-11, border-hairline, <Smartphone size={18} />
  <ol>illustrated iOS steps</ol> ← detected iOS Safari (numbered badges, shipped treatment)
  <p>{unavailable}</p>           ← everything else, 16px/400 muted
</section>
```

`IosInstallInstructions` **loses its own `<h2>`** and renders the illustrated `<ol>` only — the
section owns the single heading (D-32: "one section, one heading"). After D-34 removes the menu's
inline steps, this component has exactly **one** consumer, so the move is safe.

Visual language is deliberately **identical to the shipped Import / "Start a fresh run" blocks**:
neutral bordered `min-h-11` button, `text-[14px]/600` label, 18px leading icon, 16px muted
description beneath. No card, no gold, no new border radius — a new visual treatment here would
make the app's last section look like a different app.

### `AppMenu` — one neutral row (D-34)

Replaces **both** the gold "Install Gizz With Friends" button **and** the inline iOS steps:

| Property | Value |
|----------|-------|
| Label | **"Add to Home Screen"** — names the destination, not the action. The row navigates; calling it "Install" would be a small lie now that install lives one screen further in. |
| Icon | `Smartphone` 20px |
| Styling | `mt-3 flex min-h-11 w-full items-center gap-3 rounded-md border border-hairline px-4 text-[14px] font-semibold text-text-primary` — **byte-identical to the shipped Settings row beside it** |
| Gate | Hidden once installed (same gate as the section) |
| Action | Navigate to `#/settings`, scroll the install section into view, **move focus to its `<h2>`** |

**Retiring the accent fill here matters** — the app keeps accent for one primary CTA per surface,
and the menu's remaining rows are all neutral.

### The deep link (D-35)

`#/settings` + scroll-into-view + focus-to-heading. **No new routing concept** — hash routes stay a
validated allow-list (NAV-02). A real fragment (`#/settings#install`) was rejected: the router has
no fragment parsing and nobody will ever type the link. **The focus move is not optional**:
scrolling alone is a sighted-user affordance, and this is the phase that re-verifies VoiceOver and
keyboard. The `<h2>` carries `tabIndex={-1}` so it is programmatically focusable but not in the tab
sequence.

### Shared install state (D-33, D-36) — non-visual, but NAV-06 is dead without it

`beforeinstallprompt` is one-shot and fires early, but `useInstallState()` captures it in
**component-local** state, so a Settings section mounted later never sees it. Hoist the capture to a
**module-level singleton** (one listener at module load stashes the event); `useInstallState()`
becomes a `useSyncExternalStore` subscriber — the `pwa/bottomOverlayInset.ts` shape. This also fixes
a latent bug: `AppMenu` and `InstallBanner` each register their own listener with their own
`deferredRef` today and **can disagree about `canInstall`**. `isStandalone()` folds into the same
store (D-36) — a page cannot transition into standalone mode, so evaluating once is right; what
matters is that both gated surfaces read the **same** value. A context provider was rejected —
anything portaled outside it silently gets nothing.

**`InstallBanner` is left as-is** (D-37). NAV-05 names the instructions and the menu row, not the
banner — and the banner is what gets a new user to the relocated section. It gets a free correctness
win from the shared capture with no change of its own.

## Accessibility

- **≥44px tap targets** preserved everywhere. `ChromeToggle` is exactly 44×44 and that is an
  asserted CHROME-03 invariant, not a style choice.
- **The one timing rule** (§Sheet Timing Contract) is an accessibility contract first and a motion
  contract second: nothing may be reachable by VoiceOver or a keyboard while it is visually leaving,
  and nothing may swallow a tap while it is visually leaving.
- **Hidden chrome is removed from the a11y tree, not translated off-screen** (CHROME-04) — `inert` +
  `aria-hidden` at animation start, DOM removal at the end. A keyboard or VoiceOver user can never
  reach a control that is visually on its way out.
- **The escape control is first in tab order in the hidden state** (CHROME-03), achieved by DOM
  order alone. No positive `tabindex`.
- **The deep link moves focus, not just scroll** (D-35). A scroll-only deep link is invisible to
  keyboard and VoiceOver users — in the phase that re-verifies both.
- **Accessible names describe the next action** (`"Hide bars"` / `"Show bars"`), matching the shipped
  `"Menu"` / `"Close menu"` idiom.
- **CR-02 removes a real a11y trap**: an `aria-modal` blocker labelled "Back" that offers no Back.
- **Focus rings unchanged** — `focus-visible:outline-2 focus-visible:outline-accent` on every new
  control.
- **Reduced motion is honored per-surface via `useReducedMotion()`**, never by disabling the
  transition wholesale.
- **Installed-PWA safe areas**: `ChromeToggle` sits inside `env(safe-area-inset-top/right)` in both
  orientations, in both chrome states.
