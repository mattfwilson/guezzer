<objective>
Close CR-01: simultaneous bottom overlays overlap while `<main>` over-reserves the sum of their
heights.

The Phase-21 store already measures every registered overlay's height — it simply has no **ordering**
concept, so two visible overlays paint on top of each other at the same `bottom` while
`--gz-content-reserve` reserves both heights. Give the registrations a declared order in `config.ui`
and offset each overlay by the summed height of the visible overlays beneath it.

Purpose: this makes the Phase-21 reserve **correct** rather than merely safe, without leaving the
single-owner model. Enforcing one-overlay-at-a-time was rejected: `InstallBanner` is persistent, not
transient, so it would have to suppress or be suppressed by every toast — including the update prompt,
which is a safety surface.

Output: `offsetBelow(id)` / `useBottomOverlayOffset(id)` in the shipped store, five overlays composing
their own offset, and an **omission-detecting** guard — the one guard shape Phase 21 lacked.
</objective>

## Planner notes

**Three properties make this safe, and each must survive review:**
  1. **No feedback loop.** Offset change → re-render → `ResizeObserver` re-measure → same
     `offsetHeight` → `setBottomOverlayHeight` early-returns on an unchanged value → no notify. The
     early-return at `bottomOverlayInset.ts:57` is load-bearing; do not remove it.
  2. **`<main>` needs no change.** `--gz-content-reserve = chrome-reserve + sum(heights)` currently
     *over*-reserves because the overlays overlap; once they genuinely stack, the sum **is** the
     occupied height. The shipped `"sums multiple simultaneously-registered overlays"` case stays valid
     and becomes newly *correct* rather than merely safe.
  3. **Every hook returns a number, never an object.** That sidesteps React 19's
     uncached-`getSnapshot` infinite-loop footgun entirely. Do not "improve" it into `{offset, total}`.

**Pitfall 14 does not bite here, but say why.** `WaveToast` and `BingoCelebration` render inside
`AnimatePresence`, so an *exiting* toast keeps its last offset for the ~200ms fade. That is harmless —
it is leaving, not becoming interactive — and it is the correct behaviour anyway (a leaving toast
should not jump). Record it in a comment so a future reader does not mistake it for the frozen-props
defect that plan 22-02 exists to prevent.

**D-25 rider:** `BingoCelebration.tsx` carries a hard-coded `transition={{ duration: 0.2 }}` on its
toast, the twin of the one `WaveToast` gave up in plan 22-01. This plan touches that file, so D-25's
"prefer moving it if touched" applies — move it to `config.ui.motion.TOAST_DURATION_MS`. Leave the
supernova's `SUPERNOVA_*` timings alone; they are already named constants.

    value that is referentially stable between notifies. Comment that this is deliberate: React 19
    reports "The result of getSnapshot should be cached to avoid an infinite loop" for a fresh object,
    and returning a number makes the problem unreachable.

    concept, so two visible overlays overlapped at the same `bottom` while `<main>` reserved both. The
    declared order lives in `config.ui.BOTTOM_OVERLAY_ORDER` (bottom-most first) and the arithmetic
    lives here — the same single-owner shape as `layout/bottomSpace.ts`.

`--gz-content-reserve`'s composition in `layout/bottomSpace.ts` — the sum is now correct rather than
merely safe, which is the point.
