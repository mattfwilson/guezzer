commit with a before/after `?layoutProbe=1` capture on a reinstalled device. It is plan 22-09, Task 1.

`InstallBanner` is left completely as-is (D-37) — NAV-05 names the instructions and the menu row, not
the banner, and the banner is what gets a new user to the relocated section.

## Planner decision — the deep-link signal must survive a same-hash navigate

`22-RESEARCH.md` §Pattern 8 proposes a plain one-shot module boolean consumed by a mount-time effect.
§Pitfall 10 then shows why that is not enough: `navigate()` assigns `location.hash`, and assigning the
**same** hash dispatches no `hashchange`, so `useHashRoute`'s store never notifies and `SettingsView`
never re-renders. A user already on `#/settings` who opens the menu and taps the row would get nothing.

**Decision: make `installSectionFocus` a real `useSyncExternalStore` module holding a monotonically
incrementing counter.** `requestInstallSectionFocus()` bumps it and notifies; `SettingsView` subscribes
and runs its scroll+focus effect whenever the value changes, so a re-request while already on Settings
still fires. Same store shape as `pwa/bottomOverlayInset.ts`; the snapshot is a **number**, which
sidesteps React 19's uncached-`getSnapshot` footgun entirely.

The scroll+focus must run in a **passive** `useEffect`, not a layout effect: `AppMenu` closing restores
focus to the header Menu button at close-start in the *current* commit, and `SettingsView` mounts (or
re-renders) in a **later** commit, so a passive effect runs strictly after that restore and is not
clobbered.

`el.scrollIntoView?.(…)` must be an **optional call** — probe P8 confirms jsdom 29.1.1 has no
`scrollIntoView` and throws `is not a function`. The optional call matches this codebase's never-throw
display-helper convention (`formatMonYear`, `wakeLock.ts`, `persist.ts`) and needs no test-only shim.

**Icons:** probe P7 confirms `Smartphone` is a live export of the installed `lucide-react@1.23.0` — no
verification step is needed (assumption A4 is closed).
