## Planner decision — the meta tag is a behaviour change, so it lands alone

`22-RESEARCH.md` §Pitfall 13(b) upgrades `apple-mobile-web-app-capable` from a cosmetic tidy-up to a
**HIGH-confidence behaviour change**. Apple's reference states verbatim that
`apple-mobile-web-app-status-bar-style` — already shipped as `black-translucent` at `index.html:9` —
**has no effect unless full-screen mode is first specified via `apple-mobile-web-app-capable`**, and
that `black-translucent` displays web content on the entire screen, partially obscured by the status
bar. Adding the tag can therefore **activate** a mode that pushes content under the status bar, in the
phase whose exit control must be provably inside the safe area (CHROME-03) and whose D-13 keeps the
stage below the notch. This project has been bitten by top-inset math twice.

So: **its own atomic commit**, and a mandatory before/after `?layoutProbe=1` capture on a *reinstalled*
instance. The "before" reading is taken from the build already on the owner's device — `index.html` was
not touched in Phase 21 or anywhere else in Phase 22, so the installed shell **is** the tag-less shell,
which makes the comparison clean. If the after reading shows the top inset or `innerH` changing in a
way that pushes content under the status bar, revert that one commit; the manifest's
`"display": "standalone"` (already set in `vite.config.ts`) is what actually makes iOS launch
standalone, so reverting costs only the iOS startup-image nicety.
